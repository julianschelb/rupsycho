# Documentation Guide

This project uses [MkDocs](https://www.mkdocs.org/) with the
[Material theme](https://squidfunk.github.io/mkdocs-material/) and
[mkdocstrings](https://mkdocstrings.github.io/) for the API reference, which is generated from
Google-style docstrings. The site is published at <https://julianschelb.github.io/rupsycho/>; the
*Docs* workflow builds it on every pull request and deploys it to GitHub Pages on every push to
`main`.

## Quick commands

```bash
pip install -e ".[docs]"   # or ".[dev]"; MkDocs 2.x is not supported, the extra pins mkdocs<2
poe docs                   # serve at http://127.0.0.1:8000 with live reload
poe docs-build             # strict build into site/ (warnings are errors)
poe docs-deploy            # publish to GitHub Pages by hand (CI does this for you)
```

`site/` is git-ignored. Run `poe docs-build` before you open a pull request that touches
documentation or docstrings: the build is strict and fails on broken links and unresolved
cross-references.

## Layout

The navigation is defined in the `nav` section of `mkdocs.yml`.

| Path                         | Content                                                                                                             |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `docs/index.md`              | Home page                                                                                                           |
| `docs/getting-started.md`    | Installation and the first experiment                                                                               |
| `docs/concepts.md`           | How an experiment is structured: questionnaire, personas, models, prompt, seeds                                     |
| `docs/configuration.md`      | Reference of the JSON configuration                                                                                 |
| `docs/cli.md`                | Reference of the `rupsycho` command line                                                                            |
| `docs/tutorials/*.md`        | Task-oriented guides, one page per task (running experiments, models, post-processing, callbacks, performance, ...) |
| `docs/examples.md`           | The notebooks and example configurations in `examples/`                                                             |
| `docs/api/*.md`              | API reference, generated from docstrings with `:::` directives                                                      |
| `docs/development.md`        | Snippet include of `DEVELOPMENT.md`                                                                                 |
| `docs/changelog.md`          | Snippet include of `CHANGELOG.md` (generated by semantic-release)                                                   |
| `docs/stylesheets/extra.css` | Small style additions                                                                                               |

`DEVELOPMENT.md` and `CHANGELOG.md` live in the repository root so that GitHub shows them;
the pages in `docs/` contain only `--8<-- "DEVELOPMENT.md"` (or `"CHANGELOG.md"`), which the
`pymdownx.snippets` extension (`base_path: .`) replaces with the file. Because the same text is
rendered by GitHub and by MkDocs, use absolute URLs for links from these files to other files
of the repository; a relative link such as `CONTRIBUTING.md` would break the strict build.

## API documentation

API pages contain `::: package.module.Object` directives. To document a new public object:

1. Write a Google-style docstring with `Args:`, `Returns:`, `Raises:` and an `Example:` block.
2. Add a `:::` directive to the matching page in `docs/api/`, or create a page and add it to
   `nav` (see below).
3. Run `poe docs-build`.

````python
def my_function(param: str) -> int:
    """Short description in the imperative mood.

    Args:
        param: Description of the parameter.

    Returns:
        Description of the return value.

    Raises:
        ValueError: When the parameter is empty.

    Example:
        ```python
        my_function("text")
        ```
    """
````

The rendering options (docstring style, member filters, signatures) are set once in
`mkdocs.yml` under `plugins.mkdocstrings`. Private names (leading underscore) and objects
without a docstring are not rendered. mkdocstrings reads the source statically, so building the
documentation needs neither the model back-ends nor a GPU.

### Cross-references

Reference another documented object with its full path:

```markdown
See [`RunSummary`][rupsycho.mixins.experiment_processing.RunSummary] and the
[`seeding`][rupsycho.seeding] module.
```

The target has to be rendered by a `:::` directive on some page, otherwise the strict build
fails with *Could not find cross-reference target*. When you reference an object from a
docstring, make sure the object is part of the API pages.

## Adding pages

1. Create the Markdown file under `docs/`.
2. Add it to `nav` in `mkdocs.yml`; the strict build fails for pages that are not in the nav.
3. Link to other pages with relative links (`../concepts.md`); `poe docs-build` verifies them.

Markdown features that are enabled: admonitions (`!!! note`), collapsible blocks (`??? note`),
tables, syntax highlighting with copy buttons, snippet includes (`--8<--`) and Mermaid
diagrams in fenced code blocks tagged `mermaid`.

## Deployment

The *Docs* workflow runs `mkdocs gh-deploy --force`, which pushes the built site to the
`gh-pages` branch. Enable it once under *Settings, Pages*: deploy from the branch `gh-pages`,
folder `/ (root)`. The workflow installs only MkDocs, the Material theme and mkdocstrings
(see the `docs` extra in `pyproject.toml`), pinned to MkDocs 1.x.

## Troubleshooting

| Message of the strict build                                                    | Cause and fix                                                                                        |
| ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| `Could not find cross-reference target '...'`                                  | The target is not rendered on any page: add a `:::` directive, or fix the path                       |
| `contains a link '...', but the target is not found among documentation files` | Broken relative link, or a link to a repository file from an included file: use an absolute URL      |
| `contains a link '...', but the doc '...' does not contain an anchor '#...'`   | The heading was renamed or the anchor is misspelled (anchors are the lower-case, hyphenated heading) |
| `contains an unrecognized relative link '...'`                                 | The link is neither a page nor a URL: link pages as `page.md` and repository files with a URL        |
| `Could not collect '...'` (mkdocstrings error)                                 | The path of a `:::` directive does not exist under `src/`: check the module and object name          |
| `pages exist in the docs directory, but are not included in the "nav"`         | A page is missing from `nav` in `mkdocs.yml`                                                         |

How strict the build is, is set in the `validation` section of `mkdocs.yml`; with `--strict`
every warning fails the build.
